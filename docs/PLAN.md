# tos-chat — Plan (v1)

A chat app built to learn NestJS by doing. Users log in with GitHub, Google, or email and password, see a list of rooms, and chat in real time. Rooms are **public** (join and chat) or **private** (password required to become a member).

Agreed in a grilling session on 2026-10-28; auth replaced (Passport → Better Auth) on 2026-10-30; release scope, lesson order, and room rules updated on 2026-11-04; throttling keys and storage decided on 2026-11-05; per-user join cap and message history decided on 2026-11-06; the socket gateway and its three-lesson split decided on 2026-11-07, and corrected the same day after a Nest 12 probe showed which globals reach gateways. Changes to these decisions should be recorded here.

**v1 is released when it is deployed and people can use it in a browser.**

- Postgres: dev on `127.0.0.1:5432` (`tos_chat`), test on `127.0.0.1:5435` (`tos_chat_test`, tmpfs). Use `127.0.0.1`, not `localhost` (IPv6 `::1` does not reach the test port on this machine).
- No domain is bought until deployment (Lesson 13).
- Mail: `MAIL_DRIVER=console` in dev and tests logs verification and reset links to the Nest console.

## Auth

- **NestJS owns auth** via [Better Auth](https://better-auth.com) 1.7.x, mounted in Nest with `@thallesp/nestjs-better-auth`, Prisma adapter. Browser path: `/api/auth/*`, kept unstripped by its own web rewrite because Better Auth answers only on its `basePath` (`/api/auth`). Every other `/api/*` path is stripped.
- **Sign-in methods:** GitHub, Google (built-in social providers), and email and password. Telegram moved to v2 on 2026-11-04 (see [BACKLOG.md](./BACKLOG.md)).
- **Email and password:** `requireEmailVerification: true`, 12–128 characters, default scrypt hashing, `revokeSessionsOnPasswordReset: true`. Emails go through our `Mailer` (`ConsoleMailer` in dev and tests, `ResendMailer` in prod).
- **Sessions:** database sessions in an opaque `HttpOnly` cookie, `expiresIn` 7 days, `updateAge` 1 day, `cookieCache` 5 minutes (a revoked session can live up to 5 minutes). No JWTs, no refresh endpoint.
- **Identity:** `accountLinking` on with `trustedProviders: ["github", "google"]`: the same verified email joins one user.
- **Guarding:** the library's global `AuthGuard` (deny by default), `@AllowAnonymous()` on open routes, `@Session()` for the actor.

## Data model

```
User, Session, Account, Verification  <- Better Auth core schema, generated by its CLI into
                                        schema.prisma; our own User fields via additionalFields
RateLimit                              <- Better Auth limiter, database storage
Room(id, name unique, description?, type: PUBLIC|PRIVATE, passwordHash?, ownerId, createdAt)
Membership(userId, roomId, role: OWNER|MEMBER, joinedAt, PK(userId, roomId))
Message(id cuid, roomId, authorId, content <= 2000 chars, createdAt,
        index(roomId, createdAt, id))
```

## Rooms

- Any logged-in user can create a room and becomes its `OWNER`.
- All rooms appear in the list; private rooms show a lock and ask for the password on click.
- `POST /rooms/:id/join` creates a `Membership` (password checked for private rooms, throttled). Only members can read history or send messages.
- Owner: rename, change password, delete (messages cascade). Members: leave. Owner cannot leave (deletes instead).
- `type` is fixed at creation. A private room needs a password of 8–128 characters; a public room cannot have one.
- Joining is safe to repeat: an existing member gets 200 with no password check. A wrong or missing password gets 403, not 401, because the web redirects 401 to `/login`.
- Leaving is safe to repeat: a non-member gets 204. The owner gets 403.
- Changing the password keeps existing members. In v1 an owner can only remove a member by deleting the room; removing members is a v2 item in [BACKLOG.md](./BACKLOG.md).

## Messages

- Only members can read history. `RoomsModule` exports `RoomsService`, whose `assertMember(userId, roomId)` gives 404 for a missing room and 403 for a non-member. `MessagesService` and `ChatGateway` both use it.
- `GET /rooms/:id/messages` returns `{ items: MessageView[], nextCursor: string | null }`, newest first. `limit` defaults to 30; over 50 gives 422, not a silent reduction. The query fetches `limit + 1` rows to detect the last page, with no count query.
- Each `MessageView` includes `author` as a `UserView` (`id`, `displayName`, `avatarUrl`), loaded with `select`.
- The cursor is an opaque base64url string of `(createdAt, id)`, compared by hand as `createdAt <= x AND (createdAt < x OR (createdAt = x AND id < y))`. The first condition is redundant, but only it lets Postgres start the index scan at the cursor: on 50,000 messages in a room it cut a deep page from 6,779 buffers to 10. A malformed cursor gives 422. Prisma's `cursor: { id }` was declined: it looks up the cursor row on every query, so a hard-deleted cursor message returns 0 rows and no error, which reads as the end of history.
- Deleting a room or a user cascades to their messages (`Message.author` uses `onDelete: Cascade`, like `Room.owner`). v1 has no route that deletes an account.

## REST (behind `/api` from the browser)

- `/api/auth/*`: Better Auth's endpoints (sign-in, callbacks, sign-up, verify, reset, sign-out, get-session, link). Not hand-written.
- `GET /me`
- `GET /rooms`, `POST /rooms`, `PATCH /rooms/:id`, `DELETE /rooms/:id`
- `POST /rooms/:id/join`, `POST /rooms/:id/leave`
- `GET /rooms/:id/messages?cursor=&limit=` (cursor pagination, newest first)

## Socket contract

`ChatGateway` uses `@WebSocketGateway()` defaults: namespace `/`, path `/socket.io`, no CORS option (same origin through Next in dev; tests connect to `app.listen(0)`). Event names and payloads are typed in `@tos-chat/shared` as `ClientToServerEvents`, `ServerToClientEvents`, and `Ack<T>`.

| Direction | Event | Payload |
| --- | --- | --- |
| client → server | `room:join` | `{ roomId }` → ack `{ roomId }`. Member only; subscribes the socket to `room:<roomId>`. Safe to repeat. No history: that stays on REST |
| client → server | `room:leave` | `{ roomId }` → ack `{ roomId }`. Always ok, even if not subscribed |
| client → server | `message:send` | `{ roomId, content }` → ack `{ message }` |
| server → client | `message:new` | `{ message }` (saved row, server id + createdAt) |
| server → client | `room:removed` | `{ roomId, reason: 'deleted' \| 'left' }`, sent before the socket is removed from the room |
| server → client | `error` | `{ code, message }`, only for an event sent without an ack callback |

- **Handshake:** `afterInit(server)` registers `server.use(async (socket, next) => …)`, which calls `auth.api.getSession({ headers: socket.handshake.headers })`. No session → `next(err)` with `err.data.code = 'UNAUTHORIZED'`, so the client gets `connect_error` and never connects. A session → `socket.data.user`, which handlers trust as the actor; payloads never carry identity.
- **Per socket:** `handleConnection` joins the socket to `user:<userId>`, so "evict user X from room Y" is `server.in('user:X').socketsLeave('room:Y')`.
- **Membership vs subscription:** membership (database) authorizes; subscription (`socket.join`, in memory, lost on reconnect) only controls delivery. `room:join` and `message:send` each call `RoomsService.assertMember`. `message:send` does **not** require a prior `room:join`.
- **Send:** `content` is trimmed and must be 1–2000 characters. The gateway calls `MessagesService.create` (persist first), acks `{ ok: true, data: { message } }`, then broadcasts `message:new` with `socket.to('room:<roomId>')`: everyone except the sending socket, so the sender's other tabs still get it and the sender never dedupes its own message.
- **Acks and errors:** every client → server event acks `{ ok: true, data } | { ok: false, error: ApiError }`. A handler returns the ok ack; `WsApiExceptionFilter` turns `WsException` and HTTP exceptions (404/403 from `assertMember`, 422 from validation, 429 from the throttler) into `ApiError` and calls the ack, or emits `error` when the client sent no ack callback.
- **Which globals reach gateways (Nest 12.2.0, proven by a probe on 2026-11-07):** global guards (`AuthGuard`, `UserThrottlerGuard`) and the global `ValidationPipe` **do** run on every gateway event; `@nestjs/websockets` builds their context creators with the app config. The global exception filter does **not**: without one, errors go to Nest's default `exception` event and no ack is sent. So `ChatGateway` binds only `@UseFilters(WsApiExceptionFilter)`. Payload DTOs on `@MessageBody()` are validated by the global pipe, with the same 422 `fields`.
- **Session on every event:** the library's global `AuthGuard` calls `getSession` with the handshake headers on every event (once the 5-minute cookie cache runs out, that is a database lookup per event). A session revoked since the handshake gives a 401 `UNAUTHORIZED` ack, and `WsApiExceptionFilter` then disconnects the socket, so it stops receiving `message:new`.
- **Throttle:** the global `UserThrottlerGuard` already runs on socket events, keyed on the user that `AuthGuard` sets on the socket: 100/min per user per event. L-08a makes it socket-aware (`getRequestResponse` for `ws`, no headers on sockets), because the stock guard throws `TypeError` on an event with no payload. L-08b adds `@Throttle` for 10 per 10 s per user on `message:send`. Over the limit gives 429 `TOO_MANY_REQUESTS` with the wait in `message` ("Try again in N s"); `ApiError` gets no new field.
- **Evictions:** `RoomsService` emits `room.deleted { roomId }` and `membership.left { roomId, userId }` with `@nestjs/event-emitter`, only after the write succeeds. `ChatGateway` sends `room:removed` and then calls `socketsLeave` (the whole room for a delete, `user:<userId>` for a leave).
- **Revoked sessions:** caught on the socket's next event (above). A socket that only listens and never sends keeps receiving until it disconnects. Accepted for v1; a timed re-check is in [BACKLOG.md](./BACKLOG.md).

Membership is created over REST only; the socket only subscribes. Messages are persisted first, then broadcast.

## Frontend architecture

Agreed 2026-10-28. The how-to lives in `.claude/rules/web-*.md`; this section records the decisions.

- **Style:** `nextjs-app-architecture` (feature-sliced RSC) wins over `vercel-composition-patterns`, which wins over `vercel-react-best-practices`.
- **Server-first:** `<domain>-queries.ts` (server-only) and `<domain>-actions.ts` (`'use server'`) call Nest through `lib/api-server.ts`, which forwards cookies. The web never touches Prisma or Postgres.
- **Live-chat exception:** `features/message` seeds TanStack Query from the server, pages older history through `lib/api-client.ts`, applies `message:new` from Socket.IO, and sends via `message:send` with an ack. There is no second write path.
- **Features:** `user`, `room` (membership folded in), `message`; the socket client lives in `lib/socket/`. No `features/chat/`.
- **Session:** `src/proxy.ts` only redirects to `/login` when there is no Better Auth session cookie (UX only). No token refresh. Nest is the only authority.
- **Caching:** dynamic by default under Suspense, with `refresh()` after writes. `'use cache'` only for non-personal data whose every write goes through a Next action.
- **Errors:** `lib/api-server.ts` maps 401 → `/login`, 404 → `notFound()`, 403 → `ForbiddenError`, 400/422 → action result, 5xx → error boundary.
- **Forms:** actions validate with zod (mirroring Nest DTOs), return `{ ok: false, error, fields, values }`, and keep user input.
- **Login:** `better-auth/react`'s `createAuthClient` (same-origin `/api/auth`) for social sign-in, the email and password forms, and sign-out, in client leaves. Server components read the user through `GET /me` with forwarded cookies.
- **shadcn:** `components/ui/**` is vendor code, exempt from the composition rules.

## Backend rules

Agreed 2026-10-28. The how-to lives in `.claude/rules/api-*.md`; this section records the decisions.

- **Auth stack:** Better Auth + `@thallesp/nestjs-better-auth`, decided 2026-10-30, replacing `@nestjs/passport` + `@nestjs/jwt` before Lesson 2 was typed. Why: less auth code to own, and account linking, session revocation, email and password, and 2FA come built in. Cost: the lessons teach less about how Nest guards and strategies work inside. The official `@nestjs/authentication` (0.1.x) was declined on 2026-10-28 as pre-1.0.
- **Authorization:** the library's global `AuthGuard` (deny by default) + `@AllowAnonymous()`; record checks (membership, ownership) in services after loading.
- **Sessions:** database sessions in Better Auth's cookies (`HttpOnly`, `SameSite=Lax`, `Secure` in production). No JWTs, no refresh tokens.
- **Mail:** `MailModule` exports a `Mailer` token; `MAIL_DRIVER` (`console` | `resend`) picks `ConsoleMailer` or `ResendMailer`. Better Auth callbacks call `Mailer`, never Resend directly.
- **Data:** `prisma` / `@prisma/client` pinned to 7.10.1 with `PrismaPg`; one `PrismaService`; a repository per module; services never touch Prisma.
- **Contract:** one `ApiError { statusCode, code, message, fields? }` in `@tos-chat/shared`; validation → 422 + `fields`; response DTOs with `excludeExtraneousValues` implementing shared `*View` types; socket acks `{ ok, data } | { ok: false, error }`.
- **Structure:** modules `config`, `prisma`, `auth`, `mail`, `users`, `rooms`, `messages`, `chat`, `health`, `throttling` (added 2026-11-05: imported after `AuthModule` so its guard runs second and can read the user); `@nestjs/event-emitter` for cross-module side effects (`room.deleted`); config validated by zod.
- **Throttling:** Better Auth's limiter (database storage) on `/api/auth/*` (100/min, 10/min on sign-in); `@nestjs/throttler` 100/min default per user per route (per IP when anonymous, because server components reach Nest from the Next server's IP), 5/min per user + room and 20/min per user across rooms on every join attempt, public or private; on sockets, the same `UserThrottlerGuard` gives 100/min per user per event and 10 per 10 s per user on `message:send` (per user, not per socket, so extra tabs do not multiply the limit). Counters stay in memory for v1; a shared store is in [BACKLOG.md](./BACKLOG.md).
- **Not adopted:** Fastify, caching, API versioning, microservices (except `/health`), DDD, tracing.
